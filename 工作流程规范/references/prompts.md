# 工作流程规范 · 完整提示词(10 步)

> 使用方式:把每步提示词复制进对话,将 `【主题】` / `【你的角色】` 替换为真实内容。按规划模式(1–4) 或执行模式(5–10) 或全闭环(1–10) 顺序执行。若你只想单步(如只要交付检查 / 一页清单 / 五视角分析),直接复制对应那一步的提示词即可,不必跑全套。

> **证据与核实(通用,不绑定工具)**:涉及事实/数据时,先判断当前环境是否有实时联网检索能力。有 → 检索并标注来源链接;无 → 每条事实标 `[需核实]`,由你(用户)自行核对权威源头。**切勿编造来源或 URL。** 纯对话模式下,若你能提供权威链接/资料,请贴给我,我会优先采信你提供的而非模型记忆。

> **逐环交接(通用)**:每步须显式消费上游产物(见 SKILL.md「逐环交接 · 依赖与完成判定」表)。下游不得凭空生成上游未支撑的新事实/新方案;只跑单步时,先告诉我"你想基于什么",我绝不编造上下文。

---

## 第 0 步 · 目标对齐(开场必做,零摩擦)

```
我要推进【任务】。

在开始前,先确认我对任务的理解,避免跑偏:
- 范围:边界在哪(做哪些、不做哪些)
- 焦点:你最想解决的核心问题是什么
- 起点假设:我默认你现在已经有什么(已有代码 / 资源 / 团队 / 时间)
- 不含:明确排除什么(防止范围蔓延)
- 预期产出形态:方案文档 / 可运行代码 / 流程规范 / 交付报告

对吗?有要纠正或补充的吗?
```

> 用户回"对/确认"或纠正;纠正则重新复述一次再确认。本环节是确认而非提问,不计入后续必答数。确认后再进入下面的正式步骤。

## 第 1 步 · 五视角 STORM

```
我要推进【你的任务】。

请模拟 5 位不同的角色,从各自的视角分析这个任务:

1. 实践者:真正下场干活的人。他们会遇到哪些纸面上看不到的坑?哪些实际情况总是被忽略?
2. 学者:研究这类问题多年的人。经过验证的方法论说了什么?哪些"常识"其实站不住脚?
3. 怀疑者:认为主流做法有问题的人。最强的反方论点是什么?支持者们刻意忽略了哪些风险?
4. 成本控制者:盯着投入产出的人。钱和时间花在哪了?哪些隐性成本在影响这个任务?
5. 历史学家:见过类似项目的人。过去有什么相似的先例?那些先例最后是怎么收场的?

每个视角请给我:
- 两句话说清他的核心立场
- 支持他观点的最强证据
- 一件只有他会告诉我、其他视角绝不会提的事
```

## 第 2 步 · 矛盾图谱

```
基于上面 5 个视角,给我画一张矛盾图:
- 哪些视角在直接冲突,各自的依据是什么;
- 谁的证据最强、谁的最弱、为什么;
- 哪一个问题一旦有答案,就能化解最大的矛盾;
- 所有视角都同意的是什么(这大概率是真的);
- 没有任何视角提到的是什么(这可能是整个任务的盲区)。
```

## 第 3 步 · 综合简报

```
把 5 个视角和矛盾图综合成一份任务简报:
- 一段话总结(讲给只有 60 秒的决策者听,要细节,不要标题党);
- 5 个关键发现,按可靠性排序,标注哪些视角支持、哪些反对;
- 一个只有把 5 个视角放在一起才能看到的隐藏关联;
- 一条具体的行动建议(以我的角色【你的角色】,我该做什么不一样的事);
- 一个前沿问题(它的答案会改变我们对这个任务的全部理解)。
```

## 第 4 步 · 同行评审自检

```
现在请你对刚才这份简报做一次同行评审:
- 给 5 个关键发现逐个打 1-10 的可靠性分,并解释理由;
- 你最没把握的是哪个结论,需要什么信息才能验证它;
- 哪个视角在综合时占的比重过大了;
- 有没有第 6 个视角是该加进来、加了会改变结论的;
- 如果一位资深项目经理来评审这份简报,会打几分,会让我改什么。
```

## 第 5 步 · 方案择优

```
关于【任务】的方案太多了,我不想再收藏了。请你当一个只帮我省时间的策展人:
- 选出 3–5 个最值得考虑的执行方案(自建 / 现成工具 / 外包 / 分阶段都行);
- 每个说清楚:它为什么比同类强、该怎么做、大概要花多久、我该从它身上拿走的一个关键点;
- 再告诉我哪些是被高估的、我该躲开的坑;
- 最后把这 3–5 个排成一个推荐序,并说明各自的取舍(成本 / 时间 / 质量)。
```

## 第 6 步 · 执行阶梯

```
我想一步一步地推进【任务】,不跳过任何重要的基础。请你扮演一位专家项目经理和流程教练,把【任务】分解为 5 个清晰的难度级别,从完全新手到自信的交付者。

每个级别包括:
1. 级别名称
2. 这个阶段我应该交付什么
3. 在这个级别上"完成"是什么样子
4. 最需要重点关注的关键动作
5. 一个证明我可以进入下一级别的里程碑
6. 一个动手练习或小型试运行
7. 这个级别的执行者常犯的错误
8. 进入下一级别前的一个简单自检问题

按这个结构组织级别:
- 级别 1:完全新手
- 级别 2:基本可用
- 级别 3:标准执行
- 级别 4:问题解决者
- 级别 5:自信的交付者

解释保持实用、对初学者友好,专注于真正的进步。
```

## 第 7 步 · 啃下核心 20%(按【时间预算】伸缩)

```
我的时间预算是【时间预算】(30 分钟 / 半天 / 1 周 / 长期持续)。请据此先找出能带来 80% 实际效果的那 20% 的关键动作,解释它们为什么是核心;然后排成适配我时间预算的执行计划(30 分钟则精简到 3–4 个最核心动作 + 1 次迷你试运行;半天则 10 次课;1 周则扩展执行 + 多个交付物),每次执行/检查包含:执行目标、关键动作、一个动手练习、一个推荐资源(最好免费)、完成后的预期结果;每次执行结束,给我 5 个自检问题;全部结束后,给我一个能证明我真的可以交付的最终交付物。
```

## 第 8 步 · 逐项检查

```
我刚完成【任务】的执行,想检查自己到底做得怎么样。请你扮演一位严格但乐于助人的质检员,通过逐项核对找出交付的边界。从 10 个检查项开始,一次只查一个。规则:
1. 检查项逐渐变难:第 1-3 项基础检查,第 4-6 项功能检查,第 7-8 项质量检查,第 9-10 项验收级检查。
2. 一次只检查一项,等我给出执行情况。
3. 每项检查之后:给出判定(通过 / 不通过);告诉我哪里做对了;指出确切的差距、错误或薄弱点;给出可执行的补救动作。
4. 如果我做得偏弱,先追问一个细节,再进入下一项。
5. 如果我做得很好,适当增加检查严格度。
6. 最后给我:最终评定、我最强的环节、我最弱的环节、一份简短的整改计划、5 个最终挑战项。
7. 若我没有提前告诉你当前进度,第 1 项用中等粒度探测,再根据我的回答动态调整后续检查粒度。
不要一次给我所有结论。让这像一场真实的交付验收。
```

## 第 9 步 · 复述确认循环

```
我想用复述确认法吃透【任务/交付标准】。请你当一个有耐心的流程伙伴:先用简单的词、生活里的例子把它讲给我听,就当我 12 岁;然后让我用自己的话复述一遍;接着找出我复述里每一个含糊、跳步、绕不过去的地方,只重新教这些部分;再让我讲一遍。循环下去,直到我的复述简单、准确、完整。在我讲清楚之前,别进入新内容。
```

## 第 10 步 · 一页交付清单

```
给我做一份关于【任务/交付物】的一页交付清单,让我在交付之前,花 5 分钟就能过完:
- 一句大白话定义(交付物是什么);
- 最重要的交付标准、检查项、步骤,全用短条目,别用长段落;
- 3-5 个真实场景的例子;
- 新手最容易犯的错、最容易混淆的地方;
- 一份"上场前"检查清单;
- 最后加 5 个快问快答,测测我还记得多少。

## 第 10.5 步 · 导出 HTML 交付卡(可选,需你触发)

我想把上面这些成果做成一个可保存的交付卡。请读取 assets/template.html,把已产出的内容填进对应占位符,生成一张单文件 HTML 交付卡:
- {{TITLE}} ← 任务/交付物
- {{ROLE}} {{BUDGET}} {{GOAL}} ← 第 1 步任务画像
- {{LADDER}} ← 第 6 步执行阶梯(每级一行 .lvl:级别名 + 一句话说明)
- {{FLASHCARDS}} ← 第 10 步交付清单(每张 .flash:检查项 + 标准)
- {{QUESTION_BANK}} ← 第 8 步检查项(每题 .qa:问题 + 参考标准)
视觉按 references/design.md:中性蓝/青/琥珀、圆角无阴影、系统字体、零外部依赖。只收尾、不引入新内容。

> 只有你说「导出 HTML / 生成交付卡」才执行;默认仍是 Markdown 输出。若你只要交付清单或检查项(不要整张卡),说「只导出交付清单」/「只导出检查项」,则只渲染对应 {{FLASHCARDS}} / {{QUESTION_BANK}} 段,其余占位符留空。
```
